# D48 — retain GPU geometry during material rebinding

2026-10-16 · PH4-T04 stage B · Codex under D17, subject to D36.

For a same-scale surface paint change, keep the existing Three.js BufferGeometry, position/normal/UV BufferAttributes and geometry lease. Replace only draw groups and material leases. Compare all structural buffer values and entity/category identity, rather than revision numbers or hashes, before selecting this path. Any actual attribute/topology change retains the authoritative replacement path. Canonical document/schema/commands and worker tags do not change.

Acquire every new material lease before releasing the old material leases. Retain the first owner lease, which belongs to the existing structural geometry. Validate contiguous triangle groups and complete coverage before mutation. If validation, material acquisition or cleanup fails, the existing adapter fail-closed path disposes the entire owned scene; it cannot advertise a partly rebound scene as current. The resource pool also owns acquired leases that have not yet been attached to an object, so a late acquisition failure still closes them.

The existing batched path keeps its initial triangle order, BufferGeometry and entityRanges, including sourceStart. For each retained range, find the current source mesh by category plus entity ID; intersect its original source interval with the current material groups and map the intersections into batch-local vertex indices. Binary search skips earlier source groups. Coalesce adjacent equal material IDs. This supports a formerly single-white group splitting into left/right paint without moving triangles or invalidating picking IDs. Real structural changes still rebuild batches. Ceiling visibility and its dedicated material remain separate even if a legal project material is named __ceiling.

`lastChanges.replaced` retains its established meaning: a changed MeshData descriptor. It has never guaranteed a new THREE.Mesh object, and now it also does not imply a new GPU buffer. Existing exact changed-ID assertions remain unchanged. Buffer/attribute identities, disposal counts and actual WebGL bufferData calls provide separate allocation evidence. No diagnostic was falsified or test weakened to make the new path pass.

Trade-offs: repeated paints can leave more draw groups in the initially material-packed batches than a full repack would produce. This stage prioritizes correct stable ownership during edits; it does not tune quality profiles, device performance or claim the physical-phone 200ms target. There is no cross-frame buffer identity guarantee after an actual UV/shape change. Generic textures, palette/per-side UI and complete 2D material fills remain later work.

Verification combines analytic normal-to-side expectations on every visible sample triangle, known room/threshold materials, 20 paint/Undo-equivalent split/coalesce cycles per rendering path, exact retained geometry/attribute identities, unchanged allocation counts, actual UV/shape replacement, acquisition/coverage failure closure and 100 seeded source-interval properties. Native browser probes independently instrument actual WebGL2 bufferData, require a positive initial upload count, compare rendered PNG pixels before/after paint/Undo and preserve the original exact descriptor assertions. Scope and measured results are in verification/ph4-t04b.md and its adjacent JSON. This is Codex verification, not independent Claude-authored fixtures or a proof of all scenes/devices.

No new dependency, schema, immutable asset or accepted fixture change. No D36 account/cloud/history, mobile optimization/sharing/real-phone testing, billing/security/privacy/release/final-Claude work is started. Existing automated browser and Android debug checks are regression validation only.
