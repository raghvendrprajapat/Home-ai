## Measurement contract

`/perf` uses a private, disposable core-model store. It supports the original sample and a deterministic Codex-authored workload: 50 separate 4000 × 3000 mm centreline rooms, 200 walls/junctions, 100 dimensioned furniture placeholders and one floor. Clear area is analytically 3800 × 2800 = 10640000 mm² per room; the total wall volume is 50 × 2 × 200 × 7000 × 3000 mm³. This is not a Claude independent fixture, a furnished production scene, or the spec's distinct 100-wall F-LOW/F-MID workload.

The exported JSON records the actual initial document/hash, template hash, complete initial/final async tags, history state, viewport/DPR and changes, device metadata, workload controls and local build provenance. Prior edits are retained in the actual input. CI uses its checked `GITHUB_SHA`; local builds conservatively append `-working-tree-unverified`, with `unknown` for source archives, packed-only refs or worktrees that cannot resolve a loose reference. No Git subprocess or credentials are required to build.

- Warm-up and measured duration are separate. Three five-minute runs after 20-second warm-up are the device protocol; 5/30-second runs are marked quick diagnostics. No result automatically certifies a release.
- Whole-window FPS counts frames over the entire measured duration, including missing-draw start/end periods. `observedIntervalFps` is a separate interval statistic. Empty measurements remain `null`, rather than an invented zero.
- 2D measures RAF cadence; `editingFrameMs` selects intervals within 250 ms of a preview. Command timings include rejected/no-op attempts. `committedChanges` counts accepted generation changes; sufficient 2D interaction requires at least one accepted change, 30 previews and a command attempt. This minimum does not prove sustained five-minute dragging.
- 3D counts draw submissions only while the current scene is visible. Commit-to-submitted-draw timing begins at the canonical publish subscription, before worker request/serialization; it is not GPU completion or physical display latency. Coalesced and outstanding generations remain explicit, and pending-scene intervals are recorded.
- Draw calls, triangles and resource counts come from the renderer. Main-frame JS heap is browser-reported and approximate; worker, native and GPU memory are excluded. Unsupported readings, GPU byte usage and GPU timing remain unknown.
- Startup failures disable Start before a 3D run. Context failures, hidden pages, viewport changes and sample overflow mark interruptions. Device/thermal fields are tester-reported; ending thermal state can be annotated after completion, with its own timestamp.

The page stores reports locally for download, without uploading or changing the editor's main project. Reload clears its disposable state/reports.

## Phone instructions and pending gates

On each Low and Mid phone, in both Chrome and the later Android debug WebView:

1. Record exact phone model, RAM, Android, Chrome/WebView version, build and thermal state. Open the performance lab. Fill device/start fields before the run.
2. Select the sample, **3D**, **5 min**, **20 seconds warm-up** and scripted wall edits. Reset the test project. Wait for the first valid scene, then Start. Leave the page visible and orientation unchanged. Orbit and wall changes run automatically.
3. After completion, enter ending thermal state and tap **Record end thermal state for last run**. Reset and repeat twice; export JSON before leaving the page.
4. Repeat for the large 200-wall / 100-object 3D workload. Then select large **2D**, reset, and repeat three five-minute runs while repeatedly dragging the selected room's right corners without touching adjacent rooms. The isolated room centres have a 1000 mm gap; small moves of 400–600 mm are valid. Release periodically so accepted changes are measured. Export all reports.
5. Interrupted, partial or insufficient-interaction runs need repeating. Do not call approximate heap readings total phone/GPU memory. Compare Chrome and WebView on the same phone, with the same fixture/settings and thermal conditions.

Pending: physical Low/Mid phones and integrated-GPU desktop, three sustained runs per scenario, the separate F-LOW/F-MID scene, Android build/inspection, true display latency, texture/worker/native memory, durability and Phase 0 specialist review. Large-scene CPU work and draw-call batching must be optimized and remeasured before claiming commercial readiness. Continue independent development under D17 while retaining these release gates.
